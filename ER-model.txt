ER MODEL AND TABLE CONVERSION

The diagram uses the course notation: entity rectangles with attributes inside,
underlined primary keys, relationship diamonds, arrows toward the "one" side,
and double lines for total participation. Follows is recursive, so its two
user roles are labeled follower and followee. The dashed line connects the
followedAt relationship attribute.

ENTITY SETS
user: userId (primary key), username (unique), password, firstName, lastName.
post: postId (primary key), content, timestamp.
comment: commentId (primary key), content, timestamp.
hashtag: hashtag (primary key).
notifications: id (primary key), type, target_id, is_read, created_at.

Passwords contain hashes. Counts, follow state, last post time, and avatar
paths are calculated by the application, so they are not stored attributes.

RELATIONSHIPS
A user writes zero or more posts. Every post has exactly one author.
A user writes zero or more comments. Every comment has exactly one author.
A post has zero or more comments. Every comment belongs to exactly one post.
Each of these is one-to-many. The post/comment side has total participation.

Users like posts and bookmark posts. Both relationships are many-to-many
and optional on both sides.
Posts have hashtags. This is many-to-many and optional on both sides.
Users follow other users. This is a recursive many-to-many relationship.
A user does not have to follow anyone or have followers.
followedAt belongs to a follower/followee pair.

A user can receive many notifications. Each notification has one recipient.
A user can cause many notifications. Each notification has one actor.
Both are one-to-many, with total participation on notifications.

All five entity sets have their own primary keys, so none is a weak entity.
A comment depends on a post but still has its own independent commentId.
There is no specialization or generalization in this database.

CONVERTING TO TABLES
A one-to-many relationship becomes a foreign key on the many side.
The four many-to-many relationships become four separate tables.
Together with the five entity tables, this gives nine tables.

user(userId, username, password, firstName, lastName)
pk: (userId)
unique: (username)
not null: username
not null: password
not null: firstName
not null: lastName

post(postId, userId, content, timestamp)
pk: (postId)
fk: (userId) referencing user(userId)
not null: userId
not null: content
not null: timestamp

comment(commentId, postId, userId, content, timestamp)
pk: (commentId)
fk: (postId) referencing post(postId)
fk: (userId) referencing user(userId)
not null: postId
not null: userId
not null: content
not null: timestamp

hashtag(hashtag)
pk: (hashtag)

post_hashtag(postId, hashtag)
pk: (postId, hashtag)
fk: (postId) referencing post(postId)
fk: (hashtag) referencing hashtag(hashtag)

user_follow(followerId, followeeId, followedAt)
pk: (followerId, followeeId)
fk: (followerId) referencing user(userId)
fk: (followeeId) referencing user(userId)
not null: followedAt

likes(userId, postId)
pk: (userId, postId)
fk: (userId) referencing user(userId)
fk: (postId) referencing post(postId)

bookmarks(userId, postId)
pk: (userId, postId)
fk: (userId) referencing user(userId)
fk: (postId) referencing post(postId)

notifications(id, recipient_id, actor_id, type, target_id, is_read, created_at)
pk: (id)
fk: (recipient_id) referencing user(userId)
fk: (actor_id) referencing user(userId)
not null: recipient_id
not null: actor_id
not null: type

Primary key columns are already unique as a key and cannot be null.
Composite keys make the whole pair unique; each individual column can repeat.
All foreign keys above use ON DELETE CASCADE in database_setup.sql.
The DDL also checks minimum name/content lengths and prevents self-following.

NOTIFICATION TARGET
target_id is a post ID for LIKE, COMMENT and MENTION. It is the follower's
user ID for FOLLOW. It is nullable and has no foreign key in the current
DDL, so the diagram does not claim a database-enforced link to a target.
is_read and created_at have defaults but allow NULL in the existing schema.
The application treats NULL is_read as unread and a missing date as Unknown.
The application skips self-action notifications; the schema does not enforce
that as a CHECK constraint.
